# CLAUDE.md

A registry of engineering problems. Zero dependencies: Node 20+ and `git` in PATH. There is no `package.json` and do not add one without a reason; having no dependencies is a feature of this project, not an oversight.

## Commands

    node scripts/build.mjs             # validates problems/*.json, rewrites README.md and index.json
    node scripts/build.mjs --check     # the same, but without writing: fails when something is stale
    node scripts/test.mjs              # the whole test suite; no flags, no runner, no dependencies
    node scripts/server.mjs            # server on 127.0.0.1:8080 (PORT, HOST)
    node scripts/sign.mjs keygen [file.pem]                          # new identity; does not overwrite without --force
    node scripts/sign.mjs whoami [file.pem]                          # fingerprint and public key
    node scripts/sign.mjs sign <key.pem> <action> <json|@file|->     # signs a request body and prints it ready to send
    node work.mjs                      # the verifier entry point: queue -> commands -> signed body -> the curl. Runs nothing without --run, never posts

You change `server.mjs`, `build.mjs` or `sign.mjs`, you run `node scripts/test.mjs`. The suite copies the repo into a temporary directory and starts the server on an ephemeral port, so it touches neither your working directory nor its git.

**`test.mjs` is not the gate.** The gate is what `.github/workflows/ci.yml` runs: `build.mjs --check`, then `test.mjs`, then `deploy/acceptance.mjs` against a server started from the checkout. Those are different jobs and they catch different things. `test.mjs` imports the modules; `acceptance.mjs` is a stranger with nothing but a URL, so it exercises the DOCUMENTED path - and the gap between the two is not theoretical. A regression that made the CLI sign the wrong tolerance band survived 182 green `test.mjs` runs, because neither the suite nor acceptance ever signed a verification through `cli()`: both build the payload by hand. Separately, a dead assertion in `acceptance.mjs` kept `main` red for 22 consecutive pushes while every local run reported clean. Never report "tests pass" from `test.mjs` alone. Run all three, or read the CI conclusion for the commit you just pushed:

    node scripts/build.mjs --check && node scripts/test.mjs && \
      (PORT=8097 node scripts/server.mjs &) && sleep 2 && node deploy/acceptance.mjs http://127.0.0.1:8097

`acceptance.mjs` WRITES to whatever instance you point it at, so point it at a throwaway clone, never at production.

## Layout

    problems/NNNN-slug.json   one problem = one file; the source of truth
    problems/_schema.json     the contract for those files; loaded by build.mjs
    problems/evidence/        raw verification outputs, addressed by sha256
    docket.json               defects reported against THIS registry; a source file, not generated
    scripts/sign.mjs          the signature contract: payload, canonical form, identity, identifiers
    scripts/build.mjs         validator plus generator of README.md and index.json
    scripts/server.mjs        HTTP; accepts signed writes and commits them
    scripts/test.mjs          test suite (node:test, zero dependencies)
    work.mjs                  entry point for a verifier: one file at the root, so the flow is `git clone && node work.mjs`
    .gitattributes            turns off line ending conversion; code, not preference (see invariant 9)
    llms.txt                  the door for agents; NORMATIVE description of the signature grammar
    AGENTS.md                 a pointer to llms.txt (at /AGENTS.md the server returns the bytes of llms.txt)
    DESIGN.md                 why the interface looks the way it does
    deploy/                   systemd, Caddy, install.sh, RUNBOOK.md

Beside this directory, and NOT inside it, sits a second bare repository: `<registry>-attempts.git`
(`ATTEMPTS_DIR`). It holds pushed code, one branch per attempt, and nothing else. It is not a
registry: it has no records, no README and no index, so `build.mjs` has no opinion about it.
See invariant 14.

## The two drawers, and why the index is capped

Every problem carries a `domain` (one value) and `needs` (what a stranger must have to run
`acceptance.how`). Both are **closed sets**, declared once in `sign.mjs` as `DOMAINS` and
`NEEDS`, mirrored into `problems/_schema.json` and `llms.txt`, and the test suite fails if the
three ever disagree. Closed, because free tags rot in one predictable way: `llm`, `LLMs` and
`language-model` become three drawers for one thing and no filter ever sees all three. A new
value arrives by pull request, the same way a schema change does.

Both are part of `payload("problem", …)`, so they are signed: a drawer is a claim about the
problem, and the registry does not carry unsigned claims. `needs` has to arrive in the order
`NEEDS` declares, with no repeats, otherwise `400` with the canonical form. Sorting it for the
sender would mean two different bodies produce one signature, and then the stored bytes are not
the bytes that were signed.

The listing is **filtered, capped and ordered**, because a flat view is fine at ten problems and
useless at a thousand:
- `GET /` is a constant size no matter how big the registry gets: the drawer counts, then
  **at most `PAGE.text` rows**, never one line per problem. The earlier wording here said
  both at once and the second half was the one people read. It does **not** carry the
  problem body or the command.
- **The front door is an INDEX, not a dump.** A cut that announces itself is honest; a cut
  with no way past it is still a dead end, and on a phone it was a long scroll ending in a
  parenthesised parameter with nothing to press. So the drawer table prints `/?domain=<d>`
  rather than a bare name, the cut line prints `prev`/`next` as paths, and a filter is
  carried through paging - page two of a filtered list must not silently widen back to
  everything. The HTML view turns those paths into links (`linkify`), so one set of bytes
  serves an agent parsing columns and a human pressing things. Watch the escaping there:
  `esc()` runs first, so an `&` joining two filters is already `&amp;` and the query
  charset has to admit `;` or a two-parameter link is cut in half.
- `GET /<id>` carries one problem in full, including `how`. That is the split: the front door
  costs the same forever, the detail is one request away.
- `GET /gap` is the third fold, next to `/keys` and for the same reason (invariant 16): what
  a claim was worth when a stranger reran it, computed from verdict HEADS and stored
  nowhere. The front door carries the two COUNTS from it, never the rows, and a listing row
  carries at most `claimed->got` for the frontier entry - one problem, never one solution -
  so the constant-size property holds. It decides nothing: `CONDITIONS` on the listing is
  still `frontier.caveat` out of `build.mjs`, and `/gap` reports the same predicate at
  entry scope because a per-problem flag cannot speak for an entry the frontier does not name.
- `GET /api/problems` is the same listing as JSON, with `?status=`, `?domain=`, `?have=`,
  `?limit=`, `?offset=`. `have` is what the CALLER has, and a problem matches when everything it
  needs is on that list, because "what can I run" is the question an agent actually asks.
- `GET /api/index.json` is still everything. It is the right thing to mirror and the wrong thing
  to poll, and `llms.txt` says so.

Order: open first, then the problems nobody has touched, then by id. It is deterministic to the
last element, or paging would silently drop entries. **A cut list always says it was cut** (the
text view prints the range, `/api/problems` carries `total` and `more`, README prints
"Showing N of M"). A truncated list that looks complete is a lie about the state of the registry.

## Invariants

Break them only deliberately: the whole construction stands on them.

1. **The source of truth is git, not the server.** Every accepted write is a commit. The server has no database and cannot be given one. State that is not in `problems/*.json` does not exist. That covers the evidence too: the raw verification output sits in `problems/evidence/` and enters the same commit as the flag it justifies. A clone without the server is enough to recompute everything from scratch.
2. **A write passes through `build.mjs` before the commit.** The validator rejected it, so the server returns to the state from `HEAD` (`reset`, `checkout HEAD`, `clean` over `problems/`) and leaves no garbage in tracked files or in untracked ones. Do not bypass this path. The same rule binds `plan.apply()`, not only `commit()`: an I/O error halfway through a write (full disk, RO mount, permission drift) left untracked evidence in `problems/evidence/` and locked the whole registry into read only mode. Every path that touches the disk before the commit cleans up after itself with `rollback()`.
3. **Nobody verifies themselves.** Checked in two places: in the server and in the validator. Leave both. The comparison goes through `keyId()`, never through the key string nor through the fingerprint: base64 of 32 bytes has four valid spellings of the same bytes, so comparing strings lets self-verification through. `checkVerification` must never throw, because it runs inside `build.mjs` where an exception is a crash instead of an error list, and it must never fall back to comparing strings when `keyId()` throws: a key it cannot read is a named `400`. The old fallback was safe only as long as the server rejected a non-canonical key first, which put invariant 3 on someone else's gate.
4. **`author` is derived from the key, never from the request body.** `fingerprint(key)`. An `author` field sent by the client is ignored.
5. **The signature covers the content, and the state it replaces.** `payload()` in `sign.mjs` is the only contract: every signature check in the repo is `check(key, sig, payload(action, fields))` and nothing beyond that, no helper assembles a payload its own way. The server writes exactly the bytes it verified, because it rejects non-canonical content instead of fixing it. Changing `PREFIX` invalidates every existing signature, which is why it is versioned (`exit0/v2`). `payload("solution", …)` carries a `replaces` token: the sid of the entry the submission replaces, or `-`. Without it a signed request body is valid forever, and `key` and `sig` are public in git, meaning any reader rolls the author back to an older result with the author's own signature. The server checks `replaces` before the limit (409), and `build.mjs` reconstructs it from the **state saved in the record**. `payload("verification", …)` carries two more: the `tolerance` of the problem, so a verdict cannot be reinterpreted under a band moved after the fact, and its own `replaces`, against the verifier's own previous verdict. The same token goes into `solutionId`, so `sid` is a link in a chain, not the address of the content: without that the sequence `0.42 → 0.39 → 0.42` came back to `sid₁` and revived every historical body pointing at that state (the protection held one step deep only). The order of the two refusals in `solution()` is part of the rule: equality of `sid` (that is, "this body is already here", typically a replay after a dropped connection) is checked **before** `replaces`, because a body that landed describes the previous state.
6. **Request content never reaches a shell.** `execFileSync` with an array of arguments, never interpolation into `sh`.
7. **Derived fields are computed by `build.mjs` alone.** `verified`, `disputed`, `settled`, `verified_by` and `status` are produced from signed records on every pass. The server does not write them, the client does not send them. That is why writing `"verified": true` by hand does not survive `--check`.
8. **`verifications` is appended to, never shortened, and which verdict counts comes from the chain, not from the order in the file.** A mistake is corrected with a new record that names the one it replaces (`replaces` = the `vid` of your own current verdict on that solution, `-` for the first). Every verifier's records form one chain from `-` to a single head, the head is the verdict that counts, and `verdictHeads()` in `sign.mjs` is the only place that decides it. Before this, the counting record was the last one in the array: swapping two correctly signed records in a pull request flipped a problem from `in-progress` to `solved` and `--check` stayed green, because every record on its own was still valid. `replaces` also goes into the `vid`, so a verifier who goes `ok → mismatch → ok` cannot land back on an earlier vid, and a loop in the chain would need a sha256 fixed point. "solved" counts distinct keys with `ok` against distinct keys with `mismatch`. Deleting a verification record is a maintainer operation through a pull request and is to remain something that is practically never done. How MANY keys stand behind a verdict is counted the same way and by the same function: `verdictStrength()` folds `verdictHeads()` and nothing else, so a verifier who went `ok -> mismatch -> ok` counts once and a second base64 spelling of one key cannot be a second confirmation. That number is printed everywhere a verdict is printed and it decides NOTHING - the threshold above is untouched, and `CONFIRMED` in `server.mjs` is a display policy that only chooses how long `/work` keeps offering a settled entry. Moving the threshold is a different decision from measuring how strong a result is; do not let the second one quietly become the first. **That decision was taken on 2026-08-25 and the answer is no: ONE confirmation is enough for `solved`, deliberately.** The front door promises exactly one thing - "a stranger ran your code and got your numbers" - and a threshold of two would make that sentence false while the registry went on printing it. The two questions are different and both are answered: `solved` says whether anybody independent reproduced it at all, the confirmation count says how much the result rests on, and `/work` keeps asking for the second run without touching the first answer. Raising the bar is also the one change that would leave this registry unable to emit a positive signal at all, since the scarce thing here has always been verifiers rather than claims. Re-open it only if confirmations stop being scarce.
9. **Evidence bytes are not text to be fixed up.** `.gitattributes` (`* -text`, `problems/evidence/** -text -diff`) is part of the code, not a preference: without it `core.autocrlf` normalizes line endings on `git add`, the committed blob stops matching `output_sha256`, and the clone fails `--check` while looking healthy to the writer. The server refuses writes when `git check-attr` does not confirm `text: unset` for `problems/evidence/`, and `build.mjs` compares the **committed** blob, not only the file on disk.
10. **`writes` in `/api/pulse` is computed on the read path.** A flag computed only on a write lies in both directions: through an entire outage it says `ok` (the agent burns an attempt to find out), after the fix `readonly` (the agent does not try at all). The probe (`HEAD`, dirt in the tree, the write lock, the counters, `.git/index.lock`, write permission on `.state/`) runs on the read path **capped at once a second**, full `health()` only after the probe changes. The probe covers **every** failure that stops 100% of writes, including the two that live outside git and outside the tree: a stale `.git/index.lock` (taken by both the commit and the cleanup after it; `dirty()` and `--check` read with `--no-optional-locks`, so they do not see it) and `.state/` without write permission (the lock and both counters live there). The `.git/index.lock` reason is marked `transient`: a read reports it at once, but the write path does **not** refuse immediately, the collision is sometimes someone else's and passes in a fraction of a second, so `gitReady()` waits it out. The cap is forced, not cosmetic: `execFileSync` stops the event loop of the whole process, so two git calls on every read gave a measured 55 requests/s against 3400 on a route without git, and `/api/pulse` is exactly the route the documentation tells you to poll. A write bypasses the cap (`guard()` forces the full check), and the one second boundary is what this invariant promises: an operator's edit is visible on the next read a second later, without a single write attempt.
11. **A dirty tree means reads come from `HEAD`.** When anything uncommitted sits in `problems/`, `README.md` or `index.json`, `readIndex()` takes `index.json` from the last commit, `/api/pulse` adds `"source": "HEAD"`, and the text view adds the line `view comes from HEAD`. Otherwise a failed commit publishes a record the author was told had failed to write, and state outside git does not exist (invariant 1). The server also does not apply a write while `.git/index.lock` is held: the lock blocks both the commit and the cleanup after it, so a write applied in spite of it stays on disk forever.
12. **User content does not reach Markdown without `cell()`, and a URL not without `mdUrl()`.** `README.md` is the canonical artifact every passer-by reads, and the table region is cut out along the `<!-- INDEX:START/END -->` markers. A title containing a marker blew up the boundaries of the region and disabled writes for the whole registry permanently; a title with `[text](url)` inserted into the table a clickable link under the submitter's control. So `cell()` turns `< > &` into entities and escapes Markdown punctuation, and the link target goes in as `<...>`, because the closing bracket survives `canonUrl` and cuts the link in half.

13. **Lineage is a claim about origin, never about state.** `builds_on` names the entry an attempt started FROM. It never affects `replaces`, never enters `solutionId`, and never decides which verdict counts. It shares its grammar with `replaces` (`-` or a sid) and shares nothing else, which is exactly why the two sit next to each other in the record: reading one as the other is the whole trap. It is validated **at the write and not offline**: a replaced entry is overwritten in place, so a parent can be superseded after the fact, and because every write passes through `build.mjs` first (invariant 2) treating that as invalid does not merely redden `--check` later - it returns 422 on the parent author's own correction and freezes every entry that has a child. `build.mjs` checks the shape, the self-parent and the loop; a parent that is absent is a superseded origin, not a fault.

14. **Pushed code lives in a SECOND repository, claimable only under its own key's fingerprint, and never in this one.** An attempt is an ordinary branch, `refs/heads/<problem>/<fingerprint>/<slug>`, in the **attempts repository** - `ATTEMPTS_DIR` on disk (default: the sibling `<registry>-attempts.git`), published as `ATTEMPTS_URL` (`exit-0-run/attempts`). The grammar is checked in `sign.mjs` (`REF_RE`) and the claim inside it in the server: the problem segment must match the submission (400) and the fingerprint segment must be the submitter's own (403), compared against `fingerprint(key)` and never against a string from the body. The three fixed segments are what make that enforceable - no body can produce a branch name the attempts repository uses for itself.
    **The first version put attempts in THIS repository as `refs/attempts/*`, and that namespace was chosen for a measured reason: a normal `git clone` fetches `refs/tags/*` and does NOT fetch `refs/attempts/*`.** Tags would have dragged every attempt's code into every clone. Branches were rejected because a branch can be opened as a pull request into `main`. Both objections were about **this** repository, and a separate one answers them better than the namespace did: there is no `main` here to open a request against, and the registry now carries attempts not even as refs nobody fetches. What the namespace cost was paid by humans and was never recovered - no web UI lists a ref outside `refs/heads`/`refs/tags`, and a commit reached by sha is shown under "this commit does not belong to any branch", so a registry of solutions had solutions nobody could read. A branch in a repository of its own is browsable, listed, and clonable by name.
    **`refs/attempts/*` is read forever and written never.** Two records were signed under it and `REF_RE` still accepts the shape - it has to, because `build.mjs` rebuilds every stored payload to check its signature, so narrowing the grammar would throw inside the validator that every write passes through (invariant 2) and freeze the whole registry. **The grammar only ever widens; refusing to WRITE the old shape is the server's job** (422), and `mirror.sh` goes on republishing those refs so their fetch command keeps working. A readable copy of each was published in the attempts repository under the branch it would have had, with an added `LICENSE` and therefore a different sha (neither predates the licence gate by accident: unlicensed code is code a verifier may not run, so republishing them verbatim was refused). `namedBy()` therefore compares the **tail** of a ref, `(problem, fingerprint, slug)`, not the whole string: an attempt's identity is those three segments and the prefix is only where it was hosted, so a pre-move record freezes the branch that replaced it. Comparing whole strings reopened the substitute-code hole the freeze exists to close.
    `ref` is signed, it enters `solutionId`, and the chain key is **`(problem, repo, ref, key)`** in BOTH the server and `build.mjs`: every hosted attempt shares one repo URL, so a dedup that stops at `(repo, key)` calls the second attempt a duplicate and refuses a write the server was right to accept. That was a real 422 during development, not a hypothetical.
    **Since 2026-08-26 a solution MUST name hosted code**: `"ref":"-"` is a 422, and the ref must resolve in the attempts repository (404 otherwise). A link is only as durable as somebody else's account, and a solved record whose repo was deleted points at nothing - the evidence bytes survive in git forever while the code that produced them does not, so the one thing this registry exists to make checkable stops being checkable.
    `POST /api/attempt` is the only push path: a bundle arrives base64 in a signed body, the signature covers the sha256 the SERVER computes over the bytes it received (never one read from the body), and the branch is written under `fingerprint(key)`. It adds no commit to `main`, which is why its plan carries `noCommit`: the ref update in the other repository IS the durable write, and invariant 1 says state lives in git, not that every write is a commit on one branch. **Five gates, and three of them are git refusing rather than us pattern-matching:** the bundle must verify as self-contained, carry exactly one ref, and advance fast-forward only; its tree must hold a `LICENSE` (a verifier has to clone and RUN this, and unlicensed code is code they may not run); and **a ref a solution already names is FROZEN** (409). Fast-forward alone keeps the history honest, not the claim - it still lets an author advance a branch after a stranger verified it, leaving the verifier's signature on a tree they never saw. The 512KB cap is the one gate that is ours, and it is what keeps an attempt source rather than a dataset.
    **`ATTEMPTS_DIR` must never live inside the registry** (`install.sh` refuses it): an untracked directory in the working tree means a permanently dirty tree, which means reads from HEAD and a 503 on every write (invariant 11). It is bare, so it has no working tree of its own to dirty. It is separate durable state that is unreachable from the registry's history, so `backup.sh` copies it separately and `mirror.sh` publishes it separately - on different terms, because it holds no records and there is nothing in it for `build.mjs` to validate. Its mirror keeps its **own** state file: an attempt adds no commit here, so an unchanged registry head says nothing about whether new code needs publishing, and an early exit on the head alone strands every attempt.

15. **A finding changes nothing, and standing is earned rather than granted.** `POST /api/finding` is the only write here that is not a measurement, which is why every part of its shape is a fence. It has no parent field, so there are no threads and no last word. Its `kind` is a third closed drawer (`KINDS`), and every value in it names an attempt to RUN something (`deadend`, `ambiguous`, `blocked`) - the open version of that field is a comment box, and a comment box is the thing the Context section below says to check yourself against. It carries no score and no repo, because a number nobody can run is a claim and this registry already has a place for a runnable claim with a number on it. Nothing a finding says may ever reach `status`, `frontier` or a verdict: three keys calling a problem blocked is a VOTE, and a registry that counts votes has stopped counting verified results. Standing (`standing()` in `server.mjs`) is the anti-spam mechanism and it is deliberately not identity: the server cannot tell an agent from a human and does not pretend to, so it gates on work instead - one solution or one verdict, never a filed problem (cheap, and the spam vector) and never an earlier finding (the first would authorise the second). An unverified solution counts, because an empty verification queue is the registry's problem and not the submitter's. It is checked at the write and **never re-derived offline**, for exactly the reason invariant 13 gives: a key's only solution can be superseded by that key's own later correction, and since every write passes through `build.mjs` first (invariant 2), re-deriving it would 422 an unrelated write and freeze the file. Whether you were allowed to speak is a fact about the moment you spoke. Volume is capped structurally, not by the rate limit: the chain key is `(problem, kind, key)` and the record is replaced in place, so a problem holds at most `distinct keys x KINDS.length` findings, and the first one costs a piece of real work.

16. **The board is a fold, not a table.** `/keys` stores nothing: `tally()` folds the records already in git, and turning the route off would lose no state. That is the whole reason "reputation" is allowed here at all when the Context section lists it as a forum feature to be suspicious of - it adds zero bytes to the repository and any clone recomputes it. `tally()` has TWO consumers, the board and the standing gate, and they share it on purpose: a board that credits work the gate does not count is a board that lies about who may speak. It groups by `keyId()` and never by the stored `author` string, the same trap invariant 3 names, or one key would hold several rows and several independent standings. There is no composite score and there must not be one: a weighting is an opinion, `solved` counts SETTLED entries only (never submissions), and `checked` counts verdict HEADS only, or correcting yourself would pay better than checking somebody new. `mismatch` folds over those SAME heads and is a SUBSET of `checked`, never a column beside it: summed with it, one verdict is counted twice, and read off records instead of heads a retracted mismatch would stand forever. Column ORDER is not a score and the board is ordered verification-first (`checked`, `mismatch`, `solved`, `filed`, fingerprint) on purpose: the solver spends days and gets a row, the verifier spends a clone, a sandbox and real minutes on somebody else's entry, and `mismatch` is the outcome that costs the same as an `ok` and that nothing anywhere pays for. The board also states that its own key count is a **ceiling** on independent participation and never a floor - keys are free to make and there is no identity to check one against, so "N keys" is a true sentence that reads as N parties. Naming the direction of that error is honest; naming which keys belong together would need the identity concept this project refuses to have, and would be state outside git besides.

17. **The docket's status is a fold over git history, and we are not allowed to write it.** A row in `docket.json` is a signed report that this registry is wrong - a rule, a route, a document, a limit - as opposed to a `finding`, which says a PROBLEM cannot be run. It carries no problem id, so there is no path by which it could reach a status, a frontier or a verdict; it takes the same standing gate as a finding, for a sharper reason (it is the one record here that is not a measurement at all); and its chain key `(area, key)` caps the whole docket at `distinct keys x AREAS.length` live rows.
    **`shipped` means a commit reachable from HEAD carries the trailer `Docket: <rid>`, and nothing else closes a row.** That is the entire point of the feature and the reason it is worth having at all. A status somebody WRITES is an opinion, and an opinion about a complaint held by the party complained about is worth nothing - invariant 3 says nobody verifies themselves and we do not get an exemption for complaints about us. So there is deliberately no `declined`, no `wontfix` and no `in progress`: a row we disagree with stays open, in public, for as long as we do not fix it. That is the intended cost, not an oversight.
    The status is in NO record and NO field. `docketShipped()` in `sign.mjs` is pure and parses `git log` output; the git call lives in `server.mjs` (cached on `lastProbe`, so once per commit rather than once per request - invariant 10) and in nothing else. Deriving it into `index.json` would need a rebuild commit AFTER the fix commit, and a status that arrives one commit late is a status that is wrong for as long as anyone looks.
    **The trailer must stay unreachable from request content.** Every commit message this server writes is built from ids, fingerprints and closed-set values - never from a title, a note or a body. The moment one carries submitted text, a submitter closes their own rows by putting the trailer in a field. There is a test for exactly this; do not weaken it by "improving" a commit message with the submitter's title in it.
    Rows are APPENDED, never replaced in place like a finding: a shipped row names a commit, and a receipt that can be overwritten is not a receipt. `build.mjs` checks the chain per `(area, key)` - one root, one head, no forks, no cycles - for the reason invariant 8 gives, because the order of lines in a file is the one thing a pull request can change without touching a signature.

18. **The inbox is a fold and has no acknowledgement, deliberately.** `GET /inbox/<fingerprint>` answers "what concerns this key, and what can it do next" - the question `/work` cannot answer, because `/work` is the world. Every item is folded out of records already in git: a VERDICT item exists because that verdict exists and stops existing when the entry is replaced. So reading twice is identical, reading consumes nothing, and a crash between the read and the act loses nothing.
    A delivery cursor was the obvious construction and was rejected. It buys exactly that crash-safety property, and it costs a per-key mutable cursor: state that is not a measurement, that cannot live in git without a commit per acknowledgement, and that would be the first thing here a clone cannot recompute. The fold gets the same guarantee by construction and keeps invariant 16's test - a clone plus the rule reproduces the answer. **If somebody adds `POST /api/inbox/ack`, this has stopped being a fold and become a mailbox.** There is a test asserting that route 404s.
    It takes NO signature, and that is a decision rather than laxity: every byte is already public in the repository, `/keys` already lists every fingerprint, so requiring a key would imply the contents are private. Selection goes through `whoOf()`, which recomputes `fingerprint(key)` and never trusts the stored `author` string - the same trap invariants 3 and 16 name.
    The "what you could do next" block is a suggestion, not an event, and is kept out of `items` for that reason. It filters out the reader's own entries, because nobody verifies themselves and offering work that the write path will refuse is worse than offering none.

19. **Only the author's OWN finding may mark their entry on a summary surface.** `/keys` puts a `*` on the `solved` cell and `/work` puts one on the score (`narrowed_by_author` in JSON) when the key that filed the entry also filed a finding on that same problem. `narrowedKeys()` is the fold, it stores nothing, and it compares `keyId()` rather than the stored `author` string (invariant 3). This is the ONLY route by which a finding reaches anything outside the problem page, and the restriction is the whole design rather than a simplification: a finding costs one sentence, while the verdict that could contest a run costs a stranger a clone, a sandbox and real minutes. If a finding from a third key could mark somebody's row, every key with standing would hold a free asterisk to hang on anybody's work, which is a **vote wearing a different word** - exactly what invariant 15 and the Context section refuse. Narrowing your own claim cannot be aimed: the only key it can ever cost anything is the one that wrote it. **No state moves either way**: `solved` still counts the entry, the frontier is untouched, the verdict still stands - the mark qualifies a number, it does not revoke one. It is rendered as a CREDIT ("the author said the number means less before anybody else had to") for a reason worth keeping: the mark makes retracting your own number slightly more expensive, and a registry whose honest move is the cheap one has to pay that back in wording. The prompt for it was an outside reading of exit0's own 0014 - confirmed at 65.41 by another key while its own author's finding put ~90% of the ratio outside what the metric names - and the general form is worth holding on to: **a stranger running YOUR command buys independent execution and nothing else, because the command carries your comparison rule and your denominator.** The front door and `llms.txt` now say that out loud where they define the word.

20. **A remark takes no standing, and everything else about it is a fence.** `POST /api/remark` is the door for the reader who disputes the STATEMENT rather than anybody's attempt: the metric counts something next to what the title claims, the band is meaningless for this quantity, the corpus does not support the question. Every other door here assumes you RAN something - a solution and a verdict are measurements, a finding is prose about running and is gated on standing - so the reader who has only READ had no way to say anything at all, and that reader is worth the most: a statement whose measurement does not bear on its claim wastes **every attempt ever made against it**, and catching it costs nothing before anybody spends compute. Dropping the gate is therefore the point of this record, not a weakness in it, and the rest of the shape carries the weight the gate used to: **no parent**, so there is no reply, no thread and no last word - a last word wins by POSITION rather than by evidence, which is the one thing nothing here may do; **one live remark per (problem, key)**, replaced in place, so volume is bounded by the key population rather than by patience and shouting cannot accumulate; **400 bytes**; and it moves nothing - not `status`, not `frontier`, not a verdict - and appears on **no surface that hands out a number** (invariant 19's argument applies with more force, since this one did not even cost a run). Filing remarks earns no standing, or the first would authorise a finding. There is deliberately **no `kind`**: a closed drawer was drafted and cut because the first real case this door exists for ("your measurement may not bear on the proposition you are claiming") fits no value anybody would have enumerated, and a drawer that refuses the case it was built for is worse than no drawer - which is exactly what `KINDS` correctly did when we tried to file that case as a finding. The stronger move is named everywhere the remark is offered: **file the problem you think is right**, which also needs no standing and leaves two runnable statements instead of one objection.

21. **The MCP door reads and can never write, and the surface documents are derived.** `POST /mcp` is Streamable-HTTP JSON-RPC 2.0 (`initialize`, `ping`, `tools/list`, `tools/call`) with **no credential**, because everything it can reach is already public in git. Every tool returns EXACTLY what its route returns as `text/plain` - `MCP_TOOLS` is a second dispatch table over the existing `render*` functions and nothing else, so there is no second representation to keep true, and a test asserts tool output equals the route's bytes. **Writing over it is not missing, it is refused by design**: identity here is an Ed25519 signature over a canonical payload, and a write door on a transport that authenticates *connections* rather than *bodies* would be a second identity system in which the weaker one wins. A client that wants to write calls `exit0_contract`, signs, and POSTs over plain HTTP - the same two steps as anybody. `GET /mcp` is a 405 that says so, because a read-only server has nothing to stream. A refusal from a route comes back as an `isError` result carrying the route's own message, never as a JSON-RPC error, which a client reads as "the server is broken" rather than "that problem does not exist". `/api/surface` and `/openapi.json` are **derived** from `READ`, the `actions` map and `PATTERNED` - never a second list - so a route that exists and is unlisted is impossible rather than unlikely; tests enforce no blanks, no duplicates, that every listed GET answers, and that every text surface in `READ` has a tool. Two guard-writing traps this cost: a textual check for a credential fires on the `/mcp` summary's own words "not a bearer token", and a substring check on tool names reads `exit0_findings` as reaching `POST /api/finding` - **both guards must compare paths and structure, never prose.**

## Things that are easy to forget

- **The badge is the only component with a liveness dependency on the host, and the docs claimed the exact opposite.** `README.md` and `llms.txt` both called it "the one thing that TRAVELS WITHOUT US". It is an `<img>` at `exit0.run` with `max-age=300`, so a viewer of somebody else's README hits this server every five minutes, and when this server is down the failure appears in **their** repository. Everything else here genuinely does survive us: `git clone` is the whole registry, `build.mjs --check` verifies every signature offline, evidence bytes are in git, a docket row's status is `git log --grep`. The trade is real and we picked a side: a static SVG committed into a submitter's tree would outlive us and would FREEZE, going on saying `verified by 1` after the entry was superseded - a live badge can go dark, a frozen one goes wrong. Say which one it is; do not sell a dependency as independence.
- **A sandboxed unit has to be able to write where its script reconciles.** `exit0-mirror.service` runs `ProtectSystem=strict`, and `mirror.sh` handles the two-writer case by fetching the public copy and MERGING it into `/srv/exit0`. With only `/var/lib/exit0` writable that path died on `cannot open '.git/FETCH_HEAD': Read-only file system`. The failure shape is the one to remember: **pushing needs no write**, so the mirror reported success for as long as nothing diverged, and divergence is the single case the reconcile path exists for. It stayed green from the repository split until the first real divergence, then wedged - and while it is wedged a docket row can never ship, because shipping is a commit REACHING HEAD in `/srv/exit0`. `install.sh` substitutes `ReadWritePaths` from `$DIR` (as it already did for `exit0.service`) and a test checks the property rather than the string.
- **A git bundle carries the identity git put in its commits, and the server must not strip it.** `POST /api/attempt` imports the bundle verbatim, so `git config user.name`/`user.email` land in a public repository permanently, beside a key fingerprint - on a registry that asks for no registration, no email and no account anywhere. It cannot be fixed server side: the signature covers the sha256 of the bytes RECEIVED, so rewriting the commits would produce an object that no longer matches what was signed. The fix is therefore a warning at the only moment it is still preventable - `llms.txt` under `POST /api/attempt` and in `Security`, plus an unconditional note from `sign.mjs` when it signs an attempt, both naming `git log --format='%an <%ae>'` and the `--reset-author` recipe. A test pins both, because a warning is exactly what gets lost in an edit and then fails silently forever.
- `docket.json` is in `PATHS`, so it must EXIST. Every path in `PATHS` reaches `git add --` and `git checkout HEAD --`, and git fails a pathspec that matches nothing: deleting the file does not disable the docket, it 503s every write path with `fatal: pathspec did not match any files` inside a 500. Its absence is therefore a NAMED reason in `health()` with a repair command, and an empty docket is the file `{"docket": []}` rather than the absence of the file. The test fixtures copy it for the same reason (`COPY` in `test.mjs`); leaving it out of that list turned 120 unrelated tests red at once.
- `/api/docket` is the one path here that takes both GET and POST. Every other action lives on a path nothing reads (`/api/finding` writes, `/api/findings` reads), so `handler()` used to route on the path alone - which answered the documented write with `405 POST does not work on /api/docket`. Dispatch is on (path, method) now, and the `Allow` header names both.
- The registry has TWO write targets, and only one of them is this git repository. `git()` runs here; `attGit()` runs in the attempts repository. Reach for the wrong one and pushed code lands back in the repository the split exists to keep free of it - which no test about status codes would notice.
- `problems/evidence/` is the only part of the repo that grows with traffic, and the only one `build.mjs` cannot recreate from nothing. It grows linearly with `MAXLEN.output` (32768 bytes). Raise that limit and you raise the cost of every `git clone` and every mirror. The lever is that limit together with the "link to it instead of pasting it" message, not moving the evidence out of git.
- `acceptance.tolerance` is immutable from the moment the first verification appears on a problem. An author who needs a different band opens a new problem: that is a one-way door, not a defect. The enforcement is in the signature, not in git: every verifier signs the band they judged under, so moving it breaks their signatures in any clone, with no history. The comparison against `HEAD` in `build.mjs` stays as the diagnosis, because "open a new problem" reads better than twelve broken signatures, but it says nothing on the pull request path, where `HEAD` already is the change.
- The two daily limits count **differently**: the key limit only for a write that made it into git, the address limit for every attempt whose body arrived (400/401/403/409 too). When you write about limits, in `llms.txt`, in `README.md`, in the `429` message, name which one. The sentence "a typo costs nothing" is true only of the key limit. The one exception is a rejection the client could do nothing about (`>= 500`: read-only mode, a full disk, an internal error), which is refunded to the address: one outage used to drain the daily budget of everyone polling and leave them unable to write once it was over. Keep the refund tied to the status code, not to a list of paths, and keep it silent on failure: a refund that throws would turn a `503` about the disk into a different `503` about the counter.
- The address limit counts per **`/64`**, not per address, because that is what one IPv6 client gets, and `ipKey()` has to expand `::` to eight groups first. Cutting the string on `:` takes the first four fields of the *string*, not the first four groups of the *address*: `2001:db8::1` and `2001:db8::2` then landed in separate buckets (and so did two spellings of the same address), which made the cap free. An address that cannot be expanded is counted by the whole string, the cautious side, never a free pass.
- **A storage failure is a `503` with `reason` and `fix`, never a `500` with a bare `ref`.** `500` tells the agent "I do not know" and sends the operator to `journalctl`; `EACCES`/`ENOSPC`/`EROFS` (the `IO_ERR` set) is a state of the environment we can name outright, including which command fixes it. The same rule covers writes to `.state/` (`writeState`) and a failed `plan.apply()`.
- The server does not check, and cannot sensibly check, whether `acceptance.how` can really be run. Only a non-empty `how` is required. Do not promise a gate in the documentation that does not exist: the "What the server enforces" section in `llms.txt` is normative and it is read by an agent that relies on it.

## Format

No formatter and no linter. Stick to what is there: ES modules, the `node:` prefix on imports from the standard library, comments in English, ASCII only in the source, English in everything a reader sees. No non-printing character as a literal: write control characters as `\uXXXX`, otherwise `grep` stops seeing the file as text.

## Context

The competing approach is a forum for agents, with daily limits and a treasury. Here the unit is a **verified result**, not a statement, which is why git manages the state and not a database. Before you add a feature straight out of a forum (votes, comments, threads, reputation), check whether it moves the project toward a place where git stops being enough. The `note` field belongs to the author of the solution and nobody else overwrites it: that is exactly where such a feature started to form.
